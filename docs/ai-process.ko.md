# whydrop을 만들 때 Agentic AI를 어떻게 썼나

[English](ai-process.md) | **한국어**

이 기록은 **작업하면서 바로바로** 남기는 것이고, 끝난 뒤에 재구성하지 않는다. 코딩 에이전트(Claude Code)를 페어 엔지니어로 썼다. 제품에 관한 결정은 전부 사람이 내렸고, 에이전트는 조사, 초안 작성, 검토, 실측, 구현을 맡았다.

지금까지 숫자: 검토 에이전트 38개, 지적 약 550건. 채택한 지적은 실측이나 원문으로 확인했거나, 아니면 설계 결정으로 채택했다(후자는 따로 검증하지 않음). 기각하거나 바로잡은 에이전트 출력: 한 검토자가 "경쟁 도구가 UDP 지원을 거절했다"고 주장했는데, 실제 이슈 스레드를 읽어보니 사실과 달라서 쓰지 않았다.

검토와 실측에서 잡아낸 것들:
- 첫 설계대로라면 agent가 끊긴 상태에서 시작했을 때 *모든* 대상을 제외해버렸을 것이다.
- 공유기가 살아 있는지를 공유기 DNS로 판단했다면 통신사 장애가 전부 공유기 장애로 찍혔을 것이다. 그래서 닫힌 TCP 포트가 보내는 RST로 판단하도록 바꿨다 (실측 약 1.3ms).
- Linux conntrack은 첫 패킷 뒤 2초가 지나서도 패킷이 오가는 흐름에만 UDP 120초 타이머를 적용한다. 그래서 NAT 테스트는 처음 3초 동안 왕복을 이어간다 (커널 소스로 확인).
- Windows의 `time.monotonic()`은 Python 3.12 이하에서 약 15ms 단위로만 움직인다 (3.13부터는 QPC). 그래서 시간 측정은 전부 `perf_counter_ns()`로 한다.
- 무작위 패킷 손실만으로도 손실 10%에서 시간당 약 19건의 거짓 "회선 끊김"이 생길 뻔했다. 공용 대상만 투표하고, 손실 구간 안의 짧은 끊김은 그 구간의 일부로 보고하도록 고쳤더니 시뮬레이션에서 0건이 됐고, 3.0초 끊김은 여전히 전부 잡았다.
