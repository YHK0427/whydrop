# whydrop을 만들 때 Agentic AI를 어떻게 썼나

[English](ai-process.md) | **한국어**

이 기록은 **작업하면서 바로바로** 남기는 것이고, 끝난 뒤에 재구성하지 않는다. 코딩 에이전트(Claude Code)를 페어 엔지니어로 썼다. 제품에 관한 결정은 전부 사람이 내렸고, 에이전트는 조사, 초안 작성, 검토, 실측, 구현을 맡았다.

## 2026-11-17: 아이디어와 설계

| 단계 | 에이전트가 한 일 | 사람이 정한 것 |
|---|---|---|
| 문제 탐색 | 후보 아이디어를 많이 뽑음. 기억에 의존하지 않고 GitHub 실데이터(스타 수, 닫힌 기능 요청)를 확인함 | TCP와 UDP를 **둘 다** 쓸 것. 장난감이 아니라 실제 오픈소스 제품일 것 |
| 포지셔닝 | 셀프호스트 모니터링 도구들을 비교함. 집 인터넷이 *왜* 끊겼는지를 TCP와 UDP를 같이 써서 설명하는 도구가 없다는 걸 확인함 | "셀프호스트 네트워크 블랙박스"로 결정 |
| 구조 선택지 | 접근 방식 3가지(공용 서버만 / reflector 필수 / 하이브리드)와 장단점을 정리함 | 하이브리드 선택 |
| 설계 초안 | 설계 문서 작성 | 문서는 영어와 한국어로. "가라 데모 금지" |
| 빌더 점검 | 별도의 에이전트가 문서만 읽고 추측해야 하는 부분을 뽑음 | — |
| 실측 | 실제 망 두 곳에서 공용 DNS와 STUN을 UDP/TCP로 찔러봄. 실제 홈서버에서 와이파이 상태를 읽음(호스트와 컨테이너 둘 다). 공유기 RST 동작, 리졸버 경로, 커널 conntrack 기본값, Windows 타이머 해상도를 확인함 | 공유기는 사용자가 관리할 수 없음 → 공유기 장면은 폰 핫스팟으로. 같이 쓰는 홈서버에서는 와이파이 장면 금지 |
| 설계 검토 | 서로 독립된 검토 에이전트 4개가 각자 한 관점만 맡음: 네트워크 정확성, 감지 로직(끊김 타임라인 9개를 규칙에 직접 대입), 보안과 개인정보, 완결성 | — |
| 개정 | 검토 결과 반영: 구간·다수결 분석, 스스로 눈이 멀지 않는 자가 점검, nonce를 쓰는 바이트 단위 TCP 핸드셰이크, 재전송 방지, 대시보드 Origin/Host 검사, 공개용 화면 마스킹, 재현 장면 annotation, 배포 절 | 승인 / 대기 |

검토와 실측에서 잡아낸 것들:
- 첫 설계대로라면 agent가 끊긴 상태에서 시작했을 때 *모든* 대상을 제외해버렸을 것이다.
- 공유기가 살아 있는지를 공유기 DNS로 판단했다면 통신사 장애가 전부 공유기 장애로 찍혔을 것이다. 그래서 닫힌 TCP 포트가 보내는 RST로 판단하도록 바꿨다 (실측 약 1.3ms).
- Linux conntrack은 첫 패킷 뒤 2초가 지나서도 패킷이 오가는 흐름에만 UDP 120초 타이머를 적용한다. 그래서 NAT 테스트는 처음 3초 동안 왕복을 이어간다 (커널 소스로 확인).
- Windows의 `time.monotonic()`은 약 15ms 단위로만 움직인다. 그래서 시간 측정은 전부 `perf_counter_ns()`로 한다.
