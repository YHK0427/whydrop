# whydrop을 만들 때 Agentic AI를 어떻게 썼나

[English](ai-process.md) | **한국어**

이 기록은 **작업하면서 바로바로** 남기는 것이고, 끝난 뒤에 재구성하지 않는다. 코딩 에이전트(Claude Code)를 페어 엔지니어로 썼다. 제품에 관한 결정은 전부 사람이 내렸고, 에이전트는 조사, 초안 작성, 검토, 실측, 구현을 맡았다.

## 2026-11-17: 아이디어와 설계

| 단계 | 에이전트가 한 일 | 사람이 정한 것 |
|---|---|---|
| 문제 탐색 | 후보 아이디어를 많이 뽑음. 기억에 의존하지 않고 GitHub 실데이터(스타 수, 닫힌 기능 요청)를 확인함 | TCP와 UDP를 **둘 다** 쓸 것. 장난감이 아니라 실제 오픈소스 제품일 것 |
| 포지셔닝 | 이미 자리 잡은 셀프호스트 모니터링 도구들을 비교함. 처음 비교에서는 집 인터넷이 *왜* 끊겼는지를 TCP와 UDP를 같이 써서 설명하는 도구가 없었음. 하지만 나중에 실시간으로 다시 확인해보니(아래 2차 검토) 비슷한 걸 내세우는 새 도구가 있어서 이 주장은 뺌 | "셀프호스트 네트워크 블랙박스"로 결정 |
| 구조 선택지 | 접근 방식 3가지(공용 서버만 / reflector 필수 / 하이브리드)와 장단점을 정리함 | 하이브리드 선택 |
| 설계 초안 | 설계 문서 작성 | 문서는 영어와 한국어로. "가라 데모 금지" |
| 빌더 점검 | 별도의 에이전트가 문서만 읽고 추측해야 하는 부분을 뽑음 | — |
| 실측 | 실제 망 두 곳에서 공용 DNS와 STUN을 UDP/TCP로 찔러봄. Linux 호스트에서 와이파이 상태를 읽음(호스트에서 직접, 그리고 컨테이너 안에서). 공유기 RST 동작, 리졸버 경로, 커널 conntrack 기본값, Windows 타이머 해상도를 확인함 | 같이 쓰는 망을 흔들 수 있는 장면은 폰 핫스팟에서 재현함 |
| 설계 검토 | 서로 독립된 검토 에이전트 4개가 각자 한 관점만 맡음: 네트워크 정확성, 감지 로직(끊김 타임라인 9개를 규칙에 직접 대입), 보안과 개인정보, 완결성 | — |
| 개정 | 검토 결과 반영: 구간·다수결 분석, 스스로 눈이 멀지 않는 자가 점검, nonce를 쓰는 바이트 단위 TCP 핸드셰이크, 재생(replay) 공격 방지, 대시보드 Origin/Host 검사, 공개용 화면 마스킹, 재현 장면 annotation, 배포 절 | — |
| 2차 검토 | 서로 독립된 에이전트 3개를 더 씀: 경쟁 도구 실시간 재검증(GitHub API와 소스 읽기), 제품·채택 검토, 영어/한국어 일관성과 계산 감사 | 제품은 그대로 가고 초 단위 끊김 감지와 프로토콜 수준 근거로 차별화함. 노력이 중간 정도인 추가 기능(증거 내보내기, 웹훅 알림, Wireshark 분석기, 정적 데모)도 전부 넣음 |
| 현장 실측 | 설계한 1 Hz 프로브를 실제 호스트 1대에서 10분 돌림: 조용한 구간에서 사건 0건, 이벤트 루프 지연 p95 0.4ms. stdlib으로 커널 `TCP_INFO`를 읽을 수 있는지, 프로브가 VPN 경로가 아니라 실제 물리 인터페이스로 나가는지 확인함 | — |
| 문서 분리 | — | 사용자·기여자용 공개 문서는 이 레포에 두고, 내부 설계, 계획, 검토 원문, 환경 노트는 레포 밖에 둠 |
| 적대적 검토 | 설계를 검토하는 게 아니라 깨뜨리라고 지시한 에이전트 3개를 더 씀: 레드팀(끊김 타임라인을 대입하고 회선 규칙을 시뮬레이션), 회의론자(범위, 정직성, 데모 위험), 정합성·유출 감사. 에이전트는 레드팀 시뮬레이션을 다시 돌려 확인한 뒤에 받아들였고, 자기 수정안도 시뮬레이션함 | 적대적 검토를 요청함. 수정은 채택. 회의론자의 추정과 달리 기능 목록 전체를 v0.1에 넣기로 함 |

## 2026-11-20: UI/UX 설계와 구현 계획

| 단계 | 에이전트가 한 일 | 사람이 정한 것 |
|---|---|---|
| UI/UX 설계 | 설계 스킬 3개(사용성 휴리스틱, 데이터 시각화 절차, 시각 방향)를 적용함. 차트 색은 눈대중이 아니라 색각 검증 스크립트로 확인했고, 글자 대비도 계산함 (모든 글자 4.5:1 이상) | UI/UX를 처음부터 스킬을 써서 계획하라고 요청함 |
| 레퍼런스 | 비슷한 제품을 브라우저로 열어 비교함 (경쟁하는 ISP 원인 판별 도구의 라이브 데모, 상태 페이지 도구, 업타임 모니터, 경로 추적 도구, 속도 측정, 공유기 앱). 가져올 것과 피할 것을 기록함 | 비슷한 제품을 레퍼런스로 삼으라고 요청함 |
| 계획 | 작업을 일정이 붙은 계획 7개로 나눔. 첫 계획(코덱, 프로토콜, reflector)을 바이트 배치까지 정한 테스트 우선 태스크로 쓰고, 스스로 검토해서 틀린 테스트 기댓값 2개를 고침 | 범위는 전부 유지. 레포 공개 |

지금까지 숫자: 검토 에이전트 11개, 지적 약 180건. 채택한 지적은 실측이나 원문으로 확인했거나, 아니면 설계 결정으로 채택했다(후자는 따로 검증하지 않음). 기각하거나 바로잡은 에이전트 출력: 한 검토자가 "경쟁 도구가 UDP 지원을 거절했다"고 주장했는데, 실제 이슈 스레드를 읽어보니 사실과 달라서 쓰지 않았다.

검토와 실측에서 잡아낸 것들:
- 첫 설계대로라면 agent가 끊긴 상태에서 시작했을 때 *모든* 대상을 제외해버렸을 것이다.
- 공유기가 살아 있는지를 공유기 DNS로 판단했다면 통신사 장애가 전부 공유기 장애로 찍혔을 것이다. 그래서 닫힌 TCP 포트가 보내는 RST로 판단하도록 바꿨다 (실측 약 1.3ms).
- Linux conntrack은 첫 패킷 뒤 2초가 지나서도 패킷이 오가는 흐름에만 UDP 120초 타이머를 적용한다. 그래서 NAT 테스트는 처음 3초 동안 왕복을 이어간다 (커널 소스로 확인).
- Windows의 `time.monotonic()`은 Python 3.12 이하에서 약 15ms 단위로만 움직인다 (3.13부터는 QPC). 그래서 시간 측정은 전부 `perf_counter_ns()`로 한다.
- 무작위 패킷 손실만으로도 손실 10%에서 시간당 약 19건의 거짓 "회선 끊김"이 생길 뻔했다. 공용 대상만 투표하고, 손실 구간 안의 짧은 끊김은 그 구간의 일부로 보고하도록 고쳤더니 시뮬레이션에서 0건이 됐고, 3.0초 끊김은 여전히 전부 잡았다.
