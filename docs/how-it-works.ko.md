# whydrop은 어떻게 동작하나요

이 문서는 whydrop이 무엇을 보내고, TCP와 UDP에서 무엇을 알아내고, 그것으로 "어디서, 왜 끊겼나"를 어떻게 판단하는지 설명해요. 바이트 단위 와이어 형식은 [protocol](protocol.ko.md)에, 전체 규칙 표는 [design](design.ko.md)에 있어요.

## 1. 무엇을 보내나요

모든 프로브는 작고, **보낸** 시각을 기준으로 기록해요. 그래서 늦게 온 응답도 원래 속한 초에 정리돼요.

| 프로브 | 전송 방식 | 주기 | 알아내는 것 |
|---|---|---|---|
| 공유기 확인 | 닫힌 포트로 TCP SYN(RST = 살아 있음), Windows에서는 ICMP echo | 1초 | 이 기기에서 공유기에 닿는가? |
| 회선 하트비트 | UDP STUN 바인딩 요청, 여러 제공자를 돌아가며 | 1초 | 패킷이 인터넷 회선을 지나 돌아오는가? |
| DNS | 공유기, 통신사 resolver, 공개 resolver에 UDP와 TCP로 질의 | 5초 | 어느 층의 DNS가 답하는가? |
| STUN | UDP, 제공자 두 곳 | 10초 | 내 공인 IP와 매핑된 포트는? |
| TCP 연결 | 큰 공개 서비스의 443 포트로 TCP 핸드셰이크 | 2초 | TCP 핸드셰이크가 끝까지 되는가, 얼마나 걸리는가? |
| 와이파이 / 링크 | 운영체제(`iw`, `netsh`, `/sys`) | 1~2초 | 연결됐나? 어느 AP? 신호는? 케이블 신호(carrier)는? |
| udp_stream(정밀) | 내 reflector로 UDP | 0.1초 | 어떤 패킷이, 올라가다/내려오다 사라졌나? |
| hot 카나리아(정밀) | reflector로 TCP 연결 하나 | 1초 | 끊긴 동안 TCP는 무엇을 하나? |
| idle 카나리아(정밀) | 조용한 TCP 연결 하나 | 10분(설정 가능) | NAT가 쉬고 있는 연결을 잊는가? |

전체 트래픽은 기본 모드 8 kbit/s, 정밀 모드 20 kbit/s 이하로 유지돼요(테스트가 확인해요).

## 2. UDP가 알려 주는 것

UDP에는 연결도 재전송도 없어요. 사라진 데이터그램은 그냥 사라져요. 그래서 경로를 정직하게 보여 주는 증인이에요.

- **초 단위 손실.** udp_stream 패킷마다 순번이 붙어요. reflector는 각 패킷에 ECHO로 답하면서, 이 세션에서 지금까지 받은 패킷 수(`recv_count`)와 직전 32개 중 무엇을 받았는지(`rx_bitmap`)를 알려 줘요.
- **업로드인가 다운로드인가.** ECHO를 못 받은 패킷이 있을 때, 나중 ECHO의 비트맵에서 reflector가 그 패킷을 *받았다*고 나오면 ECHO가 **내려오다** 사라진 거예요. 아니면 패킷이 **올라가다** 사라진 거예요. 긴 끊김 전체는 끊김 앞뒤의 `recv_count` 차이로 합계를 내요. reflector가 세지 못한 만큼이 올라가다 사라진 양이에요.
- **재생 방지.** 모든 패킷에는 비밀값으로 만든 HMAC이 붙고, reflector는 순번 하나에 한 번만 답해요(가장 큰 순번은 재시작 뒤에도 기억해요). 그래서 reflector를 다른 사람에게 트래픽을 튕기는 데 쓸 수 없어요.
- **NAT의 동작.** STUN은 내 공인 주소와 매핑된 포트를 보여 줘요. 둘 중 하나가 바뀌면 공인 IP 변경이거나 NAT 상태 초기화예요. `nat-test`는 reflector에게 *시간이 지난 뒤에* 답해 달라고 해요. 그 늦은 답이 끝내 오지 않으면 경로의 NAT가 매핑을 잊은 거예요.

## 3. TCP가 알려 주는 것

TCP는 재전송으로 손실을 애플리케이션에게서 숨겨요. 바로 그래서 지켜볼 가치가 있어요.

- **핸드셰이크.** TCP 연결 프로브는 SYN → SYN-ACK 시간을 재요. 공유기의 닫힌 포트가 RST로 답하면, 공유기에서 아무 서비스가 돌지 않아도 공유기가 살아 있다는 증거가 돼요.
- **멈춤과 재전송.** 끊긴 동안 hot 카나리아의 하트비트에 확인 응답이 오지 않아요. Linux에서는 커널의 `TCP_INFO`로 재전송 시간 제한(RTO)이 0.2, 0.4, 0.8, 1.6초로 두 배씩 늘어나는 것과 확인받지 못한 세그먼트 수를 볼 수 있어요. 회선이 돌아와도 다음 재전송 때가 되어야 첫 확인 응답이 와요. 그래서 TCP 애플리케이션은 실제보다 끊김을 길게 느껴요.
- **리셋되나, 살아남나.** 짧은 끊김이면 연결은 살아남아요(RST 없음). NAT나 reflector가 연결을 잊었다면 다음 세그먼트에 RST가 와요. 끊김이 충분히 길면 커널이 스스로 포기해요(Windows는 이를 abort로 알리는데, whydrop은 RST가 아니라 커널 시간 초과로 기록해요).
- **쉬는 동안의 상태.** idle 카나리아는 몇 분씩 조용히 있다가 reflector가 먼저 말하게 해요. 그 ping이 끝내 오지 않으면, 조용한 동안 경로의 무언가가 연결 상태를 지운 거예요.

## 4. 프로브에서 판정까지

분석은 매초(늦은 응답까지 세기 위해 실제 시각보다 약 14초 뒤에서) 각 구간의 상태를 정해요.

1. **이 기기**: 주소나 기본 경로가 3초 동안 없음.
2. **와이파이 또는 유선**: 연결 끊김, AP 없음, 재연결, 케이블 신호 사라짐.
3. **공유기**: 공유기 확인이 연속 두 번 응답 없음 — *그리고* 그 몇 초 동안 공유기를 거쳐 인터넷에서 온 응답도 하나도 없음.
4. **인터넷 회선**: 최근 몇 초 동안 보낸 회선 프로브가 **서로 다른 제공자 두 곳 이상**, 세 번 이상에 걸쳐 모두 실패. 공유기 DNS와 통신사 DNS는 여기에 표를 던지지 않아요. 회선이 끊겨도 캐시로 답할 수 있으니까요.
5. **DNS**: 회선이 정상인데 한 종류(공유기, 통신사, 공개)의 resolver가 모두 두 번 이상 실패.

구간이 끊기면 **끊김**이 열려요. 바로 이어지는 끊김들은 합쳐요(공유기 재부팅은 끊김 세 번이 아니라 한 번이에요). 구간이 끊기지 않아도 끊김이 되는 것도 있어요. 공인 IP 변경, NAT가 잊어버린 쉬는 연결, NAT 상태 초기화.

그다음 **우선순위가 있는 규칙들**이 추정 원인을 정해요(와이파이가 먼저, 그다음 유선, 이 기기, 공유기, 공인 IP 변경, NAT, DNS, 통신사 회선 순. 공유기나 회선을 탓하기 전에 대기열을 먼저 확인해요). 끊김이 열려 있는 동안 원인은 잠정이고, 끝나고 80초 뒤 늦은 증거(1분 뒤에 보이는 공인 IP 변경 같은 것)까지 모인 다음 확정돼요.

**끊김이 아닌 것들:** 무작위 패킷 손실은 끊김이 아니라 *불안정 구간*이에요. 손실이 이어지는 기간 안의 짧은 실패는 그 일부로 보기 때문에, 손실 많은 회선이 시간당 수십 개의 가짜 끊김을 만들지 않아요. agent를 돌리는 기기 자신이 바쁘거나 잠든 시간은 모든 판정에서 빼요.

## 5. 각 개념을 어디서 볼 수 있나요

whydrop은 컴퓨터 네트워크 수업 프로젝트로 만들었어요. 다음은 화면에 드러나는 수업 주제들이에요.

| 주제 | whydrop에서 | 어디서 보나 |
|---|---|---|
| 지연, 손실, 처리량 | 프로브별 RTT, 손실, 트래픽 | 지금: 지연과 손실 줄, `/api/status` |
| DNS | UDP DNS와 TCP DNS(2바이트 길이 접두사), CHAOS 질의, 공유기 → 통신사 resolver 연결 | 내 네트워크, DNS 원인, 프로토콜 |
| UDP와 그 위에 쌓은 신뢰성 | 순번, `recv_count`, `rx_bitmap`, 재생 방지 | 끊김의 패킷 띠, 프로토콜 탭 |
| 다중화, 순번/확인 번호, RTT와 시간 제한 | UDP와 TCP가 같은 포트 하나, `TCP_INFO`의 RTO 증가, keepalive 권장 | TCP 줄, *프로토콜로 보면*, NAT 타임아웃 |
| 3-way 핸드셰이크 | 핸드셰이크 RTT, RST로 공유기 생존 확인 | TCP 연결 표본, 공유기 상태 |
| 공유기 대기열 | 대기열 규칙(끊김 직전 지연이 평소의 3배 + 50 ms 이상) | 대기열 원인, 불안정 구간 |
| IP, NAT | 공인 IP 변경, STUN 매핑 주소, NAT 유휴 타임아웃, CGNAT 단서 | NAT 타임아웃, 공인 IP 변경 끊김 |

## 6. Wireshark로 보기

[`contrib/wireshark/whydrop.lua`](../contrib/wireshark/README.ko.md)는 두 프로토콜의 모든 필드를 풀어 보여 줘요. 정밀 모드에서 끊김이 나면 답 없는 PROBE가 계속 나가는 모습, 끊김 뒤 첫 ECHO가 업로드와 다운로드를 가르는 카운터를 싣고 오는 모습, 커널이 같은 하트비트를 점점 긴 간격으로 다시 보내는 모습을 볼 수 있어요.
