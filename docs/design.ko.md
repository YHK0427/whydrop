# 설계

whydrop이 판정에 쓰는 규칙과 모든 기준값이에요. 기준값은 전부 `src/whydrop/analysis/constants.py`에 있고, `whydrop replay --set NAME=VALUE`로 기록된 DB에 다른 값을 넣어 분석을 다시 돌릴 수 있어요. 그래서 규칙을 바꾸기 전에 실제 기록으로 먼저 시험해 볼 수 있어요. 규칙의 바탕이 되는 개념은 [how-it-works](how-it-works.ko.md)를 먼저 읽어 주세요.

## whydrop이 하지 않을 것

- 업타임 모니터가 되기.
- reflector 없이는 쓸모없기. 기본 모드는 서버가 필요 없어요.
- 원인을 확실하다고 말하기. 모든 원인에는 "추정"이 붙어요(테스트가 모든 문구를 확인해요).
- 없는 끊김 만들기. 특히 이런 것들은 끊김이 아니에요. 한 번도 닿지 않은 대상, 대상 하나만 죽은 경우, agent를 돌리는 기기 자신이 멈춘 경우, reflector만 죽은 경우, 정상적인 와이파이 로밍, 회선으로 착각한 VPN 터널, 집 네트워크로 착각한 Docker Desktop VM 네트워크.
- 증폭기가 되기. reflector는 받은 것보다 많은 바이트로 답하지 않아요.
- 같은 서버의 다른 서비스를 방해하거나, 전체 8 kbit/s(기본) / 20 kbit/s(정밀)를 넘게 쓰기.

## 처리 흐름

1. **표본**: 보낸 시각을 기준으로 기록해요. 모든 프로브는 시간 제한이 지나고도 10초 더 기다리기 때문에, 늦은 응답은 손실이 아니라 늦은 것으로 세요.
2. **프레임**: 1초에 하나, 실제 시각보다 14초 뒤에서, 더는 바뀔 게 없을 때 만들어요.
3. **구간 상태**: 프레임마다 정해요(아래).
4. **끊김(인시던트)**: 구간이 끊기면 열려요. 구간이 끊기지 않아도 순간 이벤트로 열리는 것도 있어요.
5. **상태 조건**(손실, 지연, 약한 신호, 와이파이/LAN 손실, 바쁜 기기): 30초 넘게 이어지면 *불안정 구간*이 돼요. 불안정 구간에 이름을 붙일 뿐, 스스로 끊김을 열지는 않아요.
6. **원인**: 열려 있는 동안은 잠정이고, 끝나고 80초 뒤(R4의 60초 창 + STUN 주기 두 번) 확정되어 고정돼요. 이 기기, 와이파이, 케이블, 공유기가 끊겼던 경우에는 뒤따르는 회선 끊김이 합쳐질 수 있도록 120초 뒤예요(합치기 참고). 확정 원인이 잠정 원인과 다른지도 저장해요.

끊김의 끝은 회복으로 인정된 첫 성공이에요. 회선이라면 기본 회선 쿼럼 프로브의 첫 성공이에요. 카나리아(TCP 재전송 타이머 때문에 늦게 회복돼요)와 udp_stream은 아니에요.

## 구간

| 구간 | 끊김 | 회복 |
|---|---|---|
| `host_net` | 출구 인터페이스에 IPv4 주소나 기본 경로가 3초 동안 없음(전송이 기기 안에서 실패) | 주소와 경로가 돌아와 3초 유지 |
| `wifi` | up이 아님, BSSID 없음, 재연결 | BSSID와 함께 up, 3초 유지 |
| `link`(유선) | 케이블 신호(carrier) 사라짐 또는 링크 깜빡임 | 신호가 돌아와 3초 유지 |
| `lan` | 와이파이나 케이블이 살아 있는데 공유기 확인이 연속 2번 응답 없음, **그리고 그 프레임에 공유기를 거쳐 응답을 받은 회선 쿼럼 프로브가 하나도 없음**. 자체 점검 동안 공유기가 한 번도 답하지 않았다면 `lan`은 *관찰 불가*예요. 이때는 회선을 lan 없이 판정하고, 공유기와 회선 원인은 "공유기 또는 회선(구분 불가)"으로 나와요 | 공유기 응답 1번, 또는 회선 쿼럼 응답 하나 |
| `line` | `lan`이 정상이거나 관찰 불가, [T−3초, T−각 프로브의 시간 제한]에 보낸 회선 쿼럼 프로브가 **모두** 실패, 그 실패가 **제공자 2곳 이상, 3번 이상**. 시작 시각은 첫 실패 전송으로 앞당겨요. udp_stream 2초 동안 80% 이상 손실은 기본 회선 쿼럼 프로브도 함께 실패했을 때만 세요 | 회선 쿼럼 성공이 3초 이어짐 |
| `dns_router` / `dns_isp` / `dns_public` | 회선이 정상인데, 창 안에서 시도한 그 종류의 UDP resolver가 각각 2번 이상 시도해 모두 실패. 창 = 그 종류 주기의 3배. 마지막 lan/line 회복 뒤에 보낸 시도만 세요. TCP DNS는 증거로만 써요 | 성공 1번 |

**회선 쿼럼 프로브**: 회선 하트비트, STUN, 공개 DNS(UDP와 TCP), TCP 연결, 그리고 정밀 모드에서 udp_stream과 hot 카나리아. 공유기 DNS와 통신사 DNS는 절대 세지 않아요. reflector는 제공자 하나이고, 같은 회사의 두 주소도 제공자 하나예요.

**기기 안 오류와 바깥 오류**: 전송 오류는 경로 표에 그 목적지로 가는 경로가 없을 때만 기기 안 오류예요(→ `host_net`). 경로가 있는데 네트워크가 돌려보낸 오류(호스트 도달 불가, 거부, 관리상 금지)는 "공유기가 도달 불가를 알림"이라는 증거가 붙은 실패예요.

**손실 구간 게이트**: 회선 끊김 시작 전 60초 동안 회선 하트비트 손실이 5% 이상이었다면, 10초 안에 회복되는 끊김은 끊김이 아니라 손실 조건 안의 일시적 버스트예요. 시뮬레이션(기본 모드, 조건마다 1시간)에서 방향별 무작위 손실 5 / 10 / 20 / 30%는 게이트가 없으면 시간당 3 / 19 / 106 / 127개의 가짜 회선 끊김을 만들었고, 게이트가 있으면 0 / 0 / 2 / 0개였어요. 깨끗한 회선의 3초 블랙홀은 두 경우 모두 400개 중 400개를 잡았어요.

**공유기 규칙에 회선까지 보는 이유**: 와이파이 기기에서는 절전과 경합 때문에 공유기 확인이 1.5초 시간 제한을 두 번 연속 넘길 수 있어요. 그동안에도 인터넷은 같은 공유기를 거쳐 계속 답하고요. 실제 와이파이 홈서버에서 기록한 10시간을 다시 돌렸을 때, 공유기를 거친 응답이 하나도 없어야 한다는 조건을 넣자 끊김 32개 중 18개가 사라졌어요. 사라진 것은 모두 회선 프로브가 성공하던 2~7초짜리 "공유기" 끊김이었어요.

**바쁜 기기**: 측정된 이벤트 루프 지연(`agent_lag`)과 시간 제한 창이 겹치는 실패는 모든 판정에서 빼요. 기기가 절전에서 깨어나면 30초 동안은 아무것도 판정하지 않아요.

## 상태 조건

| 조건 | 기준 |
|---|---|
| 손실 | udp_stream 30초 동안 5% 이상. 기본 모드는 회선 하트비트 60초 동안 5% 이상 |
| 지연 | 30초 동안 제공자 2곳 이상에서 기준선의 3배 이상이면서 +50 ms 이상(RTT는 TCP 연결, STUN, 회선 하트비트, udp_stream, 카나리아에서. DNS는 쓰지 않음) |
| 약한 신호 | −75 dBm 이하이면서 1시간 중앙값보다 10 dB 이상 낮음 |
| 와이파이/LAN 손실 | 연결은 되어 있는데 60초 동안 공유기 확인의 10% 이상 실패 |
| 바쁜 기기 | 이벤트 루프 지연 p95 10 ms 이상 |

지연의 **기준선**: 프로브 대상별로 최근 24시간(끊김 구간 제외)의 10번째 백분위수. 처음 1시간은 판정하지 않고, 1~24시간 사이는 "학습 중"이에요.

## 합치기

- 앞 끊김이 끝나고 10초 안에 시작한 구간 끊김은 그 끊김에 합쳐요.
- 와이파이, 케이블, 공유기가 회복되고 120초 안에 시작한 회선 끊김은 그 끊김에 합쳐요. 공유기가 끊겼던 경우라면 "공유기 재시작(추정)"으로 나와요.
- 1시간이 넘으면 긴 장애로 표시해요.
- 기록 공백(agent의 30초 하트비트로 판단)은 "기록 안 함"으로 보여 주고, 재시작으로 열린 채 남은 끊김은 닫고 표시를 붙여요.

## 원인 규칙

우선순위 순서예요. 규칙이 따로 말하지 않으면 창은 끊김 시작 시각을 기준으로 해요.

| # | 추정 원인 | 조건 | 다음에 할 일 |
|---|---|---|---|
| R1a | 와이파이 문제 | [시작 − 5초, 시작 + 15초] 안에 wifi 끊김, 재연결, 로밍 | 신호가 약했다면 AP 위치나 채널을 바꾸세요. AP가 사라졌다면 전원을 확인하거나 재부팅하세요 |
| R1c | 유선 연결 문제 | 시작 ±5초 안에 link 끊김이나 깜빡임 | 케이블과 스위치 포트를 확인하세요 |
| R1d | 기기 네트워크 설정 유실 | host_net 끊김(링크는 살아 있는데 주소나 경로가 사라짐) | 기기의 네트워크 서비스를 재시작하세요. 반복되면 DHCP 임대를 확인하세요 |
| R1b | 공유기 문제 | lan 끊김, 와이파이/케이블은 정상. 링크 상태를 모르거나 출구가 VPN이면 판정하지 않음 | 공유기를 재부팅하세요. 반복되면 기록을 첨부하세요 |
| R4 | 공인 IP 변경 | 끊김 중이나 끝난 뒤 60초 안에 STUN 제공자 두 곳이 같은 새 IP를 연속 2번 알림. 혼자서도 순간 이벤트가 돼요 | 통신사가 IP를 다시 배정했어요. 자주 일어나면 기록을 들고 문의하세요 |
| R5 | NAT/방화벽 상태 유실 | idle 카나리아의 ping이 끝내 오지 않았는데, 그 앞뒤로 hot 연결과 udp_stream은 아무것도 잃지 않음 → 순간 이벤트. 쉰 시간이 측정된 타임아웃보다 길면 "만료", 아니면 "유실". 그리고: hot 카나리아의 RST와 ±10초 안의 NAT 매핑 초기화, IP 변경은 없음 → "NAT 상태 초기화" | keepalive를 nat-test가 잰 타임아웃보다 짧게 설정하세요. 초기화라면 공유기나 CGNAT 재시작을 확인하세요 |
| R3 | DNS 장애 | 회선은 정상인데 DNS 구간 끊김. 공유기만 → 공유기 DNS. 통신사만 → 통신사 DNS. 공유기 + 통신사, 공개는 정상 → 통신사 DNS 장애. 공개만 → 이 네트워크에서 공개 resolver 차단. 공개와 다른 종류가 함께 → DNS 전체 | 기기나 공유기의 DNS를 공개 DNS로 바꾸세요 |
| R2 | 회선 끊김(통신사 구간) | line 끊김, lan 정상, 출구가 VPN이 아님. 업로드/다운로드 구분은 정착 뒤에 붙어요 | 내보내기로 증거를 저장하고 통신사에 문의하세요 |
| R6 | 손실 많은 회선 | 손실 불안정 구간에 붙는 이름. 최근 60초 동안 공유기 확인도 5% 이상, 그리고 회선 손실률의 절반 이상 실패했다면 먼저 "집 안 네트워크"(다음 할 일: 와이파이 확인). 아니면 기본 모드이거나, 정밀 모드에서 회선 하트비트 손실도 2.5% 이상이면 "회선", 아니면 "reflector까지의 경로" | 증거를 저장하고 통신사에 문의하세요 |
| R7 | 높은 지연(대기열) | 지연 불안정 구간에 붙는 이름. 아래 대기열 먼저 규칙에 따라 공유기·회선 끊김의 주 원인도 돼요 | 공유기에서 SQM(cake/fq_codel)을 켜거나 업로드를 제한하세요 |
| — | 알 수 없음 | 위의 어느 것도 아님 | 버그 리포트를 첨부해 "잘못된 진단" 이슈를 올려 주세요 |

**대기열 먼저**: R1b, R2, R6을 적용하기 전에, 직전 10초의 성공 표본이 기준선의 3배 이상이면서 +50 ms 이상이었거나 회선 끊김 뒤의 실패 중 절반 이상이 늦게 돌아왔다면, R7을 주 원인으로 해요("대기열 → 시간 초과"). 어느 쪽이든 공유기 RTT도 함께 올랐다면 "집 안 대기열"이고, 다음 할 일로 SQM 대신 와이파이와 집 안 다른 기기를 가리켜요.

예: PPPoE 재접속 → R4(부 원인 R2). 와이파이로 본 공유기 재부팅 → 끊김 하나, R1a, 나중에 WAN이 돌아오는 것까지 "공유기 재시작(추정)"으로 합쳐져요. 꽉 찬 업로드 → R7.

## 보안

- **UDP**: 해시 계산 전에 44바이트가 아니거나 magic, 버전, 요청 타입이 맞지 않는 패킷은 버리고, 출발지 IP마다 초당 200개로 제한해요. HMAC이 틀리면 답 없이 버려요. 응답은 요청보다 크지 않고, NAT_REQ 하나에는 최대 2번만 답해요. HMAC을 통과한 뒤에는 출발지 IP마다 초당 50개.
- **재생**: 순번 하나에는 한 번만 답해요. 세션별 가장 큰 순번을 디스크에 7일 동안 보관하기 때문에(10초마다 기록), 가로챈 패킷을 다시 보내도 재시작 뒤까지 아무 응답이 없어요. 비정상 종료 뒤에는 마지막 10초 이내의 패킷에 한 번 답할 수 있어요(알려진 한계).
- **TCP**: 무엇이든 받기 전에 nonce 확인, 연결 수 제한.
- **비밀값**: `WHYDROP_SECRET`은 환경 변수로만, 32바이트 이상. 예시 값이면 시작하지 않아요. 로그에도 API에도 절대 나오지 않아요. 기본 모드는 비밀값이 필요 없어요.
- **agent**: 모든 ECHO와 NAT_REPLY의 HMAC, 세션, 출발지를 확인해요.
- **대시보드**: 토큰(Bearer 헤더나 WebSocket 서브프로토콜, 쿠키는 절대 안 씀), 무언가를 바꾸는 모든 요청의 사용자 정의 헤더, DNS 리바인딩을 막는 Host 허용 목록, 엄격한 Content-Security-Policy, 그리고 기기 밖으로 나가는 모든 것에 공개 보기.
- **알려진 한계**: 경로 위의 공격자는 RST를 끼워 넣어 R4나 R5를 꾸밀 수 있어요. 모든 원인에 "추정"이 붙는 이유 중 하나예요.

취약점 제보는 [SECURITY](../SECURITY.ko.md)를 보세요.

## 저장

SQLite WAL 모드, 5초마다 커밋해요(SD 카드 마모가 줄어요).

- 1초 집계는 7일 보관한 뒤 1분 집계로 합쳐요.
- 끊김 앞뒤 10분의 1초 데이터와 패킷 띠(앞뒤 60초)는 90일 보관해요.
- 남은 공간이 min(2 GB, 볼륨의 5%) 아래로 떨어지면 쓰기를 멈추고 로그에 남겨요(`storage.min_free_mb`로 기준을 바꿀 수 있어요).
- `whydrop replay`는 1초 집계와 이벤트로 분석을 다시 돌려(그래서 대략 최근 7일) 끊김을 출력할 뿐, DB에 쓰지 않아요. 결과는 근사치예요.
